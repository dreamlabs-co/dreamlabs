# Changelog

- `dreamlabs` 1.0.17 requires `dreamlabs-client` 1.0.8 or newer, below 2 (2026-10-22): public comments, docs and examples use neutral wording, with no people's names, internal results or training details. Nothing else changes.
- `dreamlabs` 1.0.10 requires `dreamlabs-client` 1.0.5 or newer, below 2, and robots requires the same (2026-10-21): the release line and main carry one version number from here; no other change from 1.0.9.
- `dreamcli setup` and `dreamcli tcp` take an arm whose chain has a continuous joint, and `dreamcli tcp` names each joint its embodiment does not drive (2026-10-18, `dreamlabs` 1.0.2). The URDF step refused such an arm when it wrote the arm file. On a Vega-1 with dexterous hands, Set tool center point was refused at the hand mount (`L_hand_mount_roll`, continuous in the URDF): "the chain takes fixed joints, and revolute and prismatic joints with limits". The arm file now builds (dream takes a continuous joint as revolute within [-pi, pi]), and with a station file whose `custom.embodiment` has a URDF joint map, the end step names each moving joint between base and end the map does not drive (the Vega-1's torso and hand mount), one line each ("torso_j1: does your robot move this joint?") with *Moves* and *Held still*, neither pressed, and holds Yes until a person picks one for each. With no embodiment or no joint map it names every moving joint of the chain; when the account cannot be asked (no key, network, auth), it says why in one line, then names every one. Held ones go in the arm file's `fixed`, so the arm is built without them. `POST /api/arm_file` takes `fixed`, and `POST /api/urdf` answers each link's joint name and `joint_map` (null in the wizard).
- `dreamlabs` 1.0.0 requires `dreamlabs-client` 1.0.0 or newer, below 2 (2026-10-19): the DreamAPI service serves the library from major 1 and refuses a 0.x client with `DA-4000 client_outdated`. No other change from 0.0.32.
- System 0's bundled tracker no longer records where it was trained (2026-10-19, `dreamlabs` 1.0.9): `tracker.npz`'s `meta` drops its `source` entry, and the station's start-up line names only the tracker's actuator and iteration. The weights are byte for byte the same.
- `dreamcli setup` no longer faults a Metal arm's grippers (0xD) at the first hand move (2026-10-19, `dreamlabs` 1.0.6): the sweep's first IK solve compiled dream's chunk IK with both arms powered, seconds of CPU that starved the arm threads, so the grippers missed their 500 ms CAN timeout ("lost contact with the computer"), both arms parked, and each gripper stayed latched (status 13) until its arm was power-cycled. Picking the robot now starts the compile on its own thread (`setup_session.warm_sweep_ik`, `setup_model.ArmModel.warm_solve`) for the one path length every sweep move solves (`setup_motion.SWEEP_TICKS`, 78 rows), and the powered checks wait for it, as their first phase on their own thread, before they power the arms, so no solve compiles under power and Start answers at once. A warm-up that fails only logs a warning, and the sweep compiles as before. The station already compiles its client's IK before the arms open (`station.warm_client_ik`).
- `dreamcli robot up` waits for the dream client's `traj` IK solve to compile before it opens the arms (2026-10-19, `dreamlabs` 1.0.6): the warm-up before the arms open (`station.warm_client_ik`) returned once the client's `tick` solve was compiled, while the client went on compiling `traj` on a thread of its own, about 5 s more on a station's CPU, and an arm opened in that window got no gripper command for over 500 ms, so its gripper faulted 0xD (on a Metal station on `dreamlabs` 1.0.1 the left arm, opened 30 ms after the warm-up's log line, faulted; the right, opened 1.6 s later, did not). The station now waits up to `station.TRAJ_WARMUP_S` (60 s) for that compile and opens the arms anyway after it, with a warning; a Start then solves with `tick` until `traj` is ready, as the client does on its own. The warm-up also no longer needs the station file to name a `checkpoint`: `dreamcli setup` writes none (a Start names the model), so a station it had just set up opened its arms with nothing compiled and its first Start faulted both grippers; the compile is the arm's, not the model's, so without one the warm-up now compiles with the first model the account lists, and says so.
- Every body's action rate is 20 Hz by default (2026-10-19, `dreamlabs` 0.0.22): a Makers Arm and an SO-101 defaulted to 30 (`config.MAKERS_CONTROL_HZ`, `config.SO101_CONTROL_HZ`, now 20, as a YAM and a Metal arm already were), and `dreamcli setup` wrote `control_hz: 30.0` into the station file of every beta robot it set up, the rate FaaS trains at (`beta_robots.json`), a Metal arm included. The wizard now writes no `control_hz`, so the body's default applies, and the example configs (`custom`, `makers`, `so101`, Seeed reBot, Trossen) say 20. A station file that names `control_hz` keeps its rate: one the wizard wrote before this release still says 30 and needs the line removed or set to 20.
- Requires `dreamlabs-client` 0.0.24 (2026-10-19, `dreamlabs` 0.0.32): a station on an arm that is not a YAM (a Metal, Makers or beta robot, an arm file) running a Dream-1 base model now asks the model to read none of its state, with the hand pose it sends kept as the anchor of the model's answer, and takes the model's null joint answer there.
- Comments, docstrings and docs in the library's public files (the robots package, the vendored IK and the shared modules) describe Dream Labs' own code by what it is, with no tracker, card or pull request numbers and no repository paths (2026-10-19, `dreamlabs` 0.0.31). Nothing else changes.
- `dreamcli setup` and `dreamcli tcp` draw a URDF's glTF meshes (2026-10-18, `dreamlabs` 0.0.27): a link whose mesh is a `.glb`, or a `.gltf` with its buffers beside it in the zip, was drawn plain, as a stick, and named as "not STL, OBJ or COLLADA". It is now drawn in the link's frame with the file's own node transforms and the URDF's scale, as ROS draws it. The page's import map pins three.js's glTF loader by hash, as it does the others. A compressed glTF (Draco or meshopt, whose decoders the page does not load) is drawn plain and named, and the rest of the arm still draws.
- `dreamcli tcp` with `DREAM_SETUP_WIZARD_V2` on draws the redesigned tool point page styled and opens it on the URDF step (2026-10-18, `dreamlabs` 0.0.27): it answered 404 for the page's stylesheet, so the page drew unstyled, and styled it opened on Choose setup method with "Step 1 of 8".
- `dreamcli setup` and `dreamcli tcp` take a URDF's folder as well as its `.zip` (2026-10-18, `dreamlabs` 0.0.27): "Choose folder" beside "Choose .zip", and a folder dropped on the redesigned page, read the same way as a zip (one URDF drawn, several listed to pick one, meshes found the same way). Both pages say "Your arm's URDF: a .zip of it with its meshes, or its folder".
- Every install hint names `pip install --upgrade dreamlabs` (2026-10-18, `dreamlabs` 0.0.21): a missing mujoco or i2rt (the end-effector speed clamp, a YAM follower), python-can (a Makers or Metal arm), PyAV (dataset videos) or the examples, and the setup wizard's version warning, said to reinstall the wheel from Setup API, to paste its install block, or `pip install "dream-robots[...]"`, a name that is not on PyPI. The library is, and `dreamlabs` carries all of them.
- Comments, docstrings and changelog entries in the package's public files name no internal people, trackers, hosts or repositories (2026-10-18, `dreamlabs` 0.0.16), its project links point at the public repository, and it requires `dreamlabs-client` 0.0.10 or newer. Nothing else changes.
- `dreamcli setup`'s camera pictures wait for a RealSense's managed exposure to hold still (2026-10-18): the preview steered it for a fixed 2 s, and from the 14 ms seed four 0.7x steps reach only about 3.4 ms, so on a test station both wrist cameras over a bright table came out white while the front camera was fine. The preview now keeps a frame once the exposure has not moved for `setup_devices.PREVIEW_STEADY_S` (0.75 s, one and a half controller steps: on target, or at a bound), giving up at the station's own settle limit, `cameras.MANAGED_SETTLE_S` (10 s). A camera already on target still takes about 0.75 s; three pictures take 30 s at worst. `PREVIEW_SETTLE_S` is gone.
- `dreamcli setup` no longer asks to unplug and replug the arms' CAN adapters after installing the udev rule (2026-10-18, `dreamlabs` 0.0.14): the replug reset the CAN bus under the arms the page had open, so both arms stopped with "a motor stopped answering". The rule now takes effect at the next reboot, and Continue and Save no longer wait for the names to be in effect; the page says to reboot before `dreamcli robot up` when they are not.
- `dreamcli robot down` with no station running switches a YAM's motors off over CAN directly, after bringing the links up (2026-10-17): a station whose PC rebooted mid-session never switched the arms off, a DM motor keeps its last command while the bus is quiet, and `robot down` only said the station was not running. Another body, or a station directory with no config, is left as before.
- Dream YAM Sim's `/seconds` accepts 1 to 86400, a day (2026-10-17): it took any size, so a trial could run, and call the model, without end, and a number past a float's range said "Updated." and then failed every task.
- `dreamcli setup`'s Find your arms says what Find arms does to the arms (each ticked adapter opened, its arm limp to move by hand, an unticked one left alone) just under Find arms, right above the question which arm moved (2026-10-16), where it was said at the top of the step, far from the Left arm and Right arm buttons.
- `dreamcli setup`'s camera detection keeps a RealSense frame from after its auto-exposure settles (2026-10-16): it kept the first frame, taken before exposure had settled, so Rebot's shots came out overexposed. The firmware's own auto-exposure stayed blown out on the Rebot's bench (about 60% of pixels clipped after 1.5 s), so the preview now runs the station's managed exposure for `setup_devices.PREVIEW_SETTLE_S` (2 s), as the Live view does, and keeps the last good frame; on a reBot station that took both wrist cameras from about 45% clipped to 0%.
- A sweep move smaller than the body's tolerance is judged by where it ended, not by its share (2026-10-16): the sweep had shrunk an SO-101's -z move to 0.3 cm, the arm read 0 of it, and the check failed it, though 0.3 cm is inside the SO-101's 1.5 cm tolerance. `setup_checks.judge_reach` now passes such a shift when it ends within the tolerance of where it was sent.

### Added

- Set tool center point in `dreamcli tcp` and `dreamcli setup` records a `digest` of the arm file and its URDF in `tcp_calibration` (2026-10-18): dream recomputes it at `policy()` and warns once when the tool point or the URDF was edited after a person set it. `kinematics.tcp_calibration()` accepts the key.

- `dreamlabs` 0.0.24 (2026-10-19): a joint-head run with `ik_solve` `traj` (every body's default) no longer compiles the trajectory solve (`dreamlabs-client` 0.0.18).


- Every body's `eef` run defaults to `ik_solve` `traj` again, the YAM's too (2026-10-18, `dreamlabs` 0.0.22): the dream client now compiles `traj` on a thread and solves its first chunks with `tick` until it is ready, so the station tests and slow machines that timed out on the compile (0.0.12) meet their deadlines; `--ik-solve tick` still runs the row-by-row solve. On a YAM, `traj` did as well as `tick` in our tests.
- `dreamlabs` 0.0.22 (2026-10-18): the `traj` IK solve no longer brakes into a chunk's padded tail or its own last rows, and runs no hard fences by default (dream-ik 0.3.1: velocity 5 / acceleration 50; `dreamlabs-client` 0.0.16). `tick` is unchanged.


- An `eef` run's IK solve (2026-10-18, `dreamlabs` 0.0.4): the station file's top-level `ik_solve` (`tick` or `traj`) and `dreamcli robot up --ik-solve tick|traj` for one run. Unset, a YAM runs `tick` (`robots.config.DEFAULT_YAM_IK_SOLVE`) and every other body `traj` (`robots.config.DEFAULT_IK_SOLVE`). An arm's `region` keeps it inside a box (the dream client's `ik` key `region`); none by default. `dreamcli --version` prints the installed library and where it came from.

- A run can take a set number of steps (2026-10-15). `StationController.start()` takes `steps`, which sticks for the runs after it like a checkpoint; the control loop (`ControlLoop(max_steps=)`, counted in `steps_done`) ends the run after that many commands to the arms, and the station then moves the arms home as after a Stop. The live agent passes a start's `prompt.steps` through and reports the count as `status.steps` (0 until a start names one: the run goes on until it is stopped, as before). A relay older than the field closes the link on `status.steps`, so the live node is deployed first.
- `dreamcli setup` draws a Seeed reBot in 3D with Seeed's own meshes, its two-finger gripper included (2026-10-17), where it drew capsules and discs with no visible gripper. A robot of one's own whose `ik` is dream's `seeed_faas` arm is drawn from `setup_view/rebot/` (`setup_view.ARM_DRAWINGS`); a custom robot on any other arm is still drawn as shapes. The meshes are built by `tests/data/setup_view_build.py rebot` from Seeed-Projects/reBot-DevArm at c16d03ea (CERN-OHL-W-2.0, the licence beside them), merged and simplified to 1.7 MB, and lined up with dream's chain on link1, since dream's joint1 sits 45 mm lower on its base than Seeed's.

- `dreamcli setup` calibrates an SO-101 (2026-10-16), so its owner never runs `lerobot-calibrate`. Step 0 no longer asks for calibration files (ticking files of one's own is optional). On step 1 an arm whose servos hold none of them still opens, to be found by moving it; once both arms are found, the page calibrates each such arm in two stages, the middle pose (drawn on dream's model) and every joint end to end with a bar per joint, and writes the servos and LeRobot's calibration file (`robots.so101_calibration`; routes `POST /api/calibrate/start`, `/middle`, `/finish`, `/cancel`). Each joint's zero is moved to where dream's `so101_faas` arm had it, from the middle of the range the joint was moved through against that arm's (`so101_calibration.reference()`), so a middle pose put by eye is enough; the page says how far each joint was off. Nothing past step 1 runs until both arms are calibrated.

### Changed

- The package ships in `dreamlabs` 0.0.5 and needs `dreamlabs-client` 0.0.5 or newer (2026-10-18), the client whose `Model.created_at` is None for a Dream Labs model. `dreamcli setup`'s reference pictures still come from the account's newest fine-tune of the robot's body, by its date, which the platform lists for an account's own fine-tunes.
- The package ships in `dreamlabs` 0.0.3 and needs `dreamlabs-client` 0.0.3 or newer, below 1 (2026-10-18): both distributions' numbering restarts at 0.0.3 for their first release on PyPI, below the 4.x they carried before, so `robots.__version__` reads `0.0.3` (`0.0.3+g<commit>` in the platform's build), and a 4.x client from before the restart no longer satisfies the requirement.
- The station's Live View is `dream.LiveViewClient` (2026-10-18): `robots.live` and `LiveAgent` are deleted, and the station builds one client and is an ordinary caller of it (`robots.station._feed_live` streams it 60 times a second, `_live_press` answers the page's buttons with the station's own calls), so the link, the encoding, the face blur and the tick guard are the client's and every station feature is open to a control loop of one's own. The `live` section is `robot_id` and `cameras`; an older file's `width_px`, `fps`, `bitrate_kbps`, `encoder` and `record` keys are ignored with one warning. Every run is now recorded by its own dream client (`robots.run.policy_config` no longer passes `_record: False`, and its `live_view` parameter is gone), which the platform takes only where `LIVE_RECORD_ONLY` is on (dev today), so until it is on in an environment a station's runs are not recorded there. The `live` extra is `dreamlabs-client[live]`.
- Every station's dream client goes sync above 900 ms (`run.SYNC_ABOVE_MS`), 1000 with System 0, whatever the body (2026-10-18). It was sized from the chunk, the rows past the 30-row execution horizon at `control_hz`, and kept the client's 700 ms below that, so a Maker Arm (30 Hz, 18 rows = 0.6 s) or an SO-101 went sync at 700 ms and held its arms through every inference at round trips of 750 to 850 ms, where a YAM ran async. `sync_above_ms` and `sys0_sync_above_ms` in the station file still replace it.
- `dreamcli setup` on a box with a screen opens the page and prints one line and one local address, no longer the box's network addresses, tailnet name and ssh tunnel (`setup_access.local_lines`); they are still printed without a screen or over ssh. The run-time errors for a missing or mismatched SO-101 calibration name `dreamcli setup` first.
- The live view encodes VP8 and the run recorder VP9, both through PyAV's libvpx; H.264 through libx264 is gone (2026-10-16). x264 is GPL licensed, and a library that opens it on every run could not be released under the Apache License, so the GPL encoders in PyAV's wheel are never opened. `live.encoder` accepts `libvpx` (the default) or `libvpx-vp9`; a file that names `libx264` or a hardware H.264 encoder fails at start-up with a message that says so. `hello` announces `vp8` and the platform's Live View page configures its decoder from it, so a station on this release needs the platform release of the same day or newer to be watched; older stations keep playing. Rollout videos are VP9 in MP4 (`video.codec` `vp9` in `meta/info.json`), which the dataset check, the training pipeline and LeRobot read as they read H.264. The page's fallback for a browser without WebCodecs plays H.264 only and now reports a VP8 stream as unsupported.
- The package ships in the library's `dreamlabs` distribution (2026-10-16; it was `dream`), which depends on `dreamlabs-client` for the client rather than carrying it, and is Apache-2.0 licensed. `robots.__version__` reads `dreamlabs` (it read `dream`), and the SO-101's missing-bus message says `pip install "dreamlabs[so101]"`. `dream-robots` itself still depends on the client, now as `dreamlabs-client>=4.0.0`.

### Changed

- A YAM runs its model's joint head unless the run names `eef` (2026-10-16), and the station's default model is `dreamlabs/dream-1-beta` (`bodies.YAM_CHECKPOINT`, was `dreamlabs/dream-1-yam`). `run.policy_config` gives a YAM `ik` `{"arm": "yam", "head": <action_space>}`: on `eef` the client solves the model's tool poses to the YAM's joints, with the pose embodiment (`adapter.YAM_POSE_EMBODIMENT`, `adapter.YAM_POSE_WIRE`: the YAM's parts and each hand's pose read, each arm's joints, tool pose and grip answered); a model with no EEF head runs its joint head, which the station log says once per run. `dreamcli robot up eef` (`robots.station --eef`, the action space `eef`) is how a run asks for that head, `dreamcli robot up joint` (or `noeef`, kept as its old name) names the default, a config file may carry `action_space` instead (`joint` unless it says `eef`), and `robot up` reports which head runs. `run.with_action_space` no longer refuses a YAM, and `bodies.check_model` passes a YAM on either action space. System 0 is unchanged: it tracks the joints the loop commands, the IK solution on the EEF head.

### Fixed

- `dreamcli setup` opens each arm again as `left` and `right` once both are named (2026-10-17), as the driver template and the README's driver table already said it did. `ArmBank.open_disengaged()` passed every driver the adapter's id as its side, also when `_reopen_both()` reopened the named arms, so a custom driver that keys its gripper's calibration by side (a Seeed reBot's on our station) never had one in setup, reported its gripper as 0 throughout, and the drawn fingers on the Home pose step never moved. `open_disengaged()` takes each device's side (`sides`); a device not named yet still opens under its id. Our own bodies use the side only as the arm's name in logs and messages, so for them only those names change.
- `dreamcli setup`'s home step names each joint outside dream's model of the arm with its reading, the range and which way to move it (a tester, 2026-10-16): "left joint 2 reads 104 degrees, the model allows -90 to 90: move it back toward 90, or your driver reads it in other units or with another zero", where it said only "left arm joints 2" and the tester had to ask what to do. `POST /api/home` adds `out_of_range`, one `{side, joint, deg, lower_deg, upper_deg}` per joint of `outside` (an SO-101's range narrowed to the one dream's model was recorded on, `so101_calibration.reference_ends()`); a reading that is not a number reads "nothing usable".
- `dreamcli setup` on a YAM + UMI (2026-10-16), two places it stopped. The URDF step confirmed an end with no moving joint between it and the base, and building the arm failed only after the tool point was set ("the chain from ... has no moving joint"); "Yes, it ends there" is now held there on both pages, with what to click. An arm that failed to open again left every later step saying only "the left arm is not open; find both arms first", the reason in the terminal; the gripper, home and SO-101 settings steps now say "the left arm is not open: <why>. Fix that, then find both arms again on step 1".
- `dreamcli setup` on an SO-101 (2026-10-16): New registered the zero-shot embodiment without `<side>_gripper`, but dream's `so101_faas` arm has a gripper drive of its own (LeRobot's 0 to 100) that the dream client sends under that part, so the client's IK refused the embodiment (`config key 'embodiment' must name one gripper part of the right arm`) and the gripper never reached the model. `adapter.zero_shot_embodiment` takes `gripper` and adds `right_gripper` and `left_gripper` last for such an arm (`ArmLayout.client_gripper`); other arms are unchanged. An account that registered `<user>/so101-faas` before this has the old layout, which New now refuses by name. Step 0 also says which calibration files the plugged-in arms hold: each SO-101 serial adapter is read once, read-only (`setup_session.so101_matches`), and a file its servos hold comes ticked with "Matches the arm on <adapter>" (`/api/state` `so101_calibrations[].matches`); before, every file came unticked with no word of which was which.
- `dreamcli robot up` (and `dreamcli motors`) brings back a CAN link a bus fault left stuck (a YAM station, 2026-10-16). Such a link keeps its UP flag with its bus not running, so it reads down, and the kernel refuses `ip link set <link> up type can bitrate 1000000` on it with `RTNETLINK answers: Device or resource busy`. `cli.bring_up_links()` now runs `sudo ip link set <link> down` first for a link that is not up but has its UP flag set, and a link that still will not come up is reported with both commands; a link whose flag is clear (the reboot case) gets the one up command as before. The setup wizard's line under a down CAN link and the install snippet after the udev rule (`setup_devices._link_up()`, which tested only the UP flag and so called a stuck link already up) give the down before the up.
- `dreamcli setup`'s Save says the platform is unavailable and to try again in a minute when the platform answers 5xx (2026-10-16), where it printed the bare `<url> answered 503: service unavailable`.

## 0.4.0 - 2026-09-11

The rate clamp caps the end effector's speed instead of every joint's step, and the station page
shows the plan against what the arms do. Minor bump because the package is pre-1.0; a 0.3.0
config file no longer loads (one key replaced) and `ControlLoop` gains a required keyword.

### Breaking

- **`max_joint_step_rad` is gone; `max_ee_speed_m_s` is required.** The station rule is a cap on
  the end effector's speed, 0.85 m/s, not on joint angular steps: a per-joint cap says nothing
  about how fast the hand moves (0.02 rad of base yaw swings an outstretched arm a centimetre,
  0.02 rad of wrist roll almost nothing), and at 0.02 rad per 20 Hz tick it throttled the policy
  on a third of all ticks of a station run (1115 clamps in 160 s, 89-91 % of ticks in two later
  runs). Every command is now clamped per arm to `max_ee_speed_m_s` metres per second, measured
  through the arm's forward kinematics from the previous command: over the cap the joint delta is
  scaled by `cap / speed`, measured once more (forward kinematics is nonlinear) and scaled again
  when still over, then accepted. The first command of a run passes (the ramp handles it) and the
  gripper keeps its `max_gripper_step`. `config.load` rejects a file still carrying
  `max_joint_step_rad` with a `ConfigError` naming `max_ee_speed_m_s`; `ControlLoop` takes
  `max_ee_speed_m_s=` (required) and `kinematics=` (per-arm, None leaves the joints unclamped for
  tests) in place of `max_joint_step_rad=` (README *Kinematics and the speed clamp*).

### Added

- **`robots.kinematics`.** `ArmKinematics.from_config(arm_cfg)` builds the YAM arm with the
  config's gripper through i2rt (`combine_arm_and_gripper_xml`) and
  `ee_position(q6)` returns the `grasp_site` position in metres after MuJoCo's `mj_kinematics`,
  with the two finger slides left at zero (they do not move the site). One `MjModel` / `MjData`
  per arm, allocated once, under a microsecond per call; `mujoco` and `i2rt` are imported lazily.
  `Kinematics` is the `Protocol` the loop takes, so tests inject linear stand-ins.
  `run.make_kinematics(cfg)` builds the pair; `StationController` keeps them for every run.
- **The plan snapshot.** `ControlLoop.plan` (`control.PlanSnapshot`, frozen, rebound per commanded
  tick like `state` and `video`): the remaining buffered rows per arm `[rows, 7]` with their due
  times relative to now, the planned end-effector speed per row (computed once at install), and
  the last `PLAN_HISTORY_S` (3 s) of commanded ticks at control rate (measured, commanded, clamped
  flag, measured end-effector speed) from fixed-size ring buffers.
- **Plan vs actual charts.** `robots.station_ui` gains a folder of viser 1.1 `add_uplot` charts
  refreshed at 5 Hz while a loop exists: per arm the joints (measured solid, commanded dashed,
  plan dotted, clamp marks) and the gripper, and one shared end-effector speed chart with the cap
  line and the clamp marks on it. `joint_chart_data`, `gripper_chart_data` and
  `ee_speed_chart_data` are pure functions (README *Plan vs actual*).
- **Clamp visibility.** `ControlLoop.max_ee_speed_requested_m_s` (the largest speed either arm
  asked for this run, before the clamp); status keys `max_ee_speed_requested_m_s` and
  `max_ee_speed_m_s`; a *Clamp* line on the status panel (clamped ticks, asked up to, cap); trace
  columns `ee_speed_l_m_s` / `ee_speed_r_m_s`; the `loop ready` line names the cap.
  `debug_scripts/preflight.py` prints each arm's zero-pose forward kinematics as a sanity line.

### Changed

- **One clamp WARNING per run**, not per burst, now that a clamp is a tuning fact rather than a
  fault: the counters and the charts carry the rest.

### Dependencies

- `hardware` extra: `mujoco>=3.1` alongside i2rt; the dev group carries `mujoco>=3.1` so the real
  model is tested where i2rt is installed. `ui` extra: `viser>=1.1` (for `add_uplot`).

### Added

- **Station agent.** `python -m robots.station --config station.yaml [--task "..."] [--ui-port 8090]
  [--api-port 8091] [--host 0.0.0.0] [--no-ui] [--inference-log PATH]` keeps a process up that opens
  both followers once and runs one `ControlLoop` at a time on request. `robots.station.StationController`
  (`start(prompt=None)`, `stop()`, `home()`, `set_prompt()`, `status()`, `close()`; states `idle`,

The rest of 0.3.0 is the work since 0.2.0 that preceded the agent, previously listed as unreleased:

### Added

- **Face blurring at capture** (`face_blur`, on by default). Every sampled camera frame has faces scrubbed
  (`shared.faceblur`, a YuNet detector) before it is encoded into the observation window and sent to DreamAPI,
  so no face ever leaves the box - not to the API, not to a serve, not to any recording. Runs on the sampled
  frames only (obs_fps, not the capture rate) and on the native BGR frame; a faceless scene costs only the
  detection. A detector that cannot load stops the camera thread (is_alive() False) rather than emit raw
  faces. Set `face_blur: false` in the station config to send raw frames (debugging/measurement only). New
  dependency: `dreamlabs-shared[faceblur]` (opencv + numpy, both already present).

### Fixed

- **Alignment after a hold.** A chunk landing after the buffer drained was installed from the
  row due by wall time, as if the arms had kept moving through the hold; on a YAM station every
  run with motion tripped an arm's supply about five seconds in, with the chunk line reading
  `36 already past` while the arms had executed a dozen rows. The loop now skips the rows
  commanded since the chunk's observation, never more than the wall clock says are due: equal
  under a continuous prefetch, only the executed count after a hold, so the plan resumes where
  the arms stopped. The line reads `chunk 3: 48 actions, 11 executed since its observation, 36
  due by wall time, after 1200 ms`. A chunk whose whole horizon is past by wall time is still
  discarded (README *Chunk alignment*).
- **Chunk alignment.** A chunk answers the observation it was computed from (row `k` is the
  target for `observed_at_s + k * period`), and lands an inference latency later, so the loop
  now drops the rows already due when it is collected and installs the rest; a chunk whose whole
  horizon has passed is discarded with a WARNING naming the latency and the horizon, and the next
  due tick refills. Installing every chunk from row 0 rewound the commanded target by the
  inference latency on every replacement, a sawtooth step per chunk that on a YAM station
  coincided with the motors dropping off the CAN bus a few seconds into motion. On the sync path
  (`refill_at_remaining: 0`) no row runs during the wait, so a chunk installs whole and the arms
  hold through the next inference; raise `refill_at_remaining` to at least `latency / period` to
  keep them moving (README *Chunk alignment*). Supersedes the 0.1.0 decision "a late
  chunk is applied from its first action"; *Alignment after a hold* above is the rule as it stands.
- **Cold pool before motion.** A warming DreamAPI pool refuses with a retryable `DA-2000` and a
  `retry_after_s` hint for about a minute; the loop re-asked on every tick and counted each empty
  tick as a stall, so it stopped after `max_stall_ticks` before any motion. After a retryable
  `DreamServerError` no refill now starts before `now + retry_after_s` (`RETRY_AFTER_DEFAULT_S`,
  1 s, when the envelope carries none), logged once per refusal at WARNING with the reason; and
  stalls count only once the first chunk has landed. Before that the loop holds the arms for up
  to the new `AppConfig.first_chunk_timeout_s` (default 120 s, positive; `ControlLoop` takes it
  as `first_chunk_timeout_s=` and `robots.run` passes it through) and then stops with
  `ControlLoopError` naming it (README *Cold pool before motion*).

### Added

- **Follower settings.** `ArmConfig` gains the driver settings our YAM stations' follower
  process launches with, at its values: `ee_mass_kg` (0.62, or null for i2rt's default) is
  passed to `get_yam_robot` as `ee_mass`; `gravity_comp_factor` (1.0, or null) is set on the
  driver as one scalar over every joint, replacing i2rt's per-joint array;
  `sdk_gripper_force_limit` (false) leaves i2rt's hardcoded 50 N gripper force limiter off
  (`_limit_gripper_force = -1.0`, with a WARNING when the driver lacks the attribute), because
  it fights the loop-side grip force cap, which is a follow-up here;
  `temp_export` (true) turns on i2rt's per-motor temperature export. `FollowerArm.from_config`
  applies them; a wrong type or range fails at load naming the key (README *ArmConfig*).
- **Gripper close-snap.** `ArmConfig.gripper_close_snap` (default 0.2, in `[0, 1]`; 0 disables)
  is stored on the arm, and `FollowerArm.write` writes a gripper target below it as 0.0, the last
  step before the wire: a policy rarely emits an exact 0, so its "closed" would leave the
  gripper hovering just open. The snapped value is what `commanded_gripper` reports and what
  `hold()` re-sends. `FollowerArm(name, robot)` built directly defaults to off.
- **Gripper effort.** `ArmState` gains `gripper_effort` (default None): i2rt's raw `gripper_eff`,
  motor torque units, when the driver reports it; the grip force cap follow-up reads it.
- **Command thread.** The tick no longer writes the arms; it submits the ramped, seamed and
  clamped command to the loop's command path, which writes both arms from its own thread at
  `command_hz`: each period it moves linearly
  from where the previous run got to toward the newest command over
  `clamp(gap between the last two submits, 1 / command_hz, command_interp_max_s)` seconds (a
  row every 33 ms is reached in about eight 4 ms steps), low-passes the result with a one-pole
  filter at `follower_smooth_hz` (`alpha = 1 - exp(-2 pi f / command_hz)`; 0 disables), and
  writes it. i2rt applies each `command_joint_pos` straight to the motor PD, so a row re-sent
  as-is at the row rate was a position staircase rather than smooth motion. A run always starts from where the
  last one got to, never from the target, so after a hold the next row is reached from where the
  arms were left, within `command_interp_max_s`. The thread starts in `__aenter__` after the
  cameras and stops in `__aexit__` before the hold or the disengage; a write that fails on it
  ends the thread and is raised by the next `step()` as the `ArmError` (or driver exception) it
  was, so the loop stops as it did. A stall or a stale frame clears the target (the thread stops
  writing, the driver keeps its last PD target) and re-holds each arm as before. New
  `AppConfig` keys: `command_hz` (250, positive), `follower_smooth_hz`
  (10, non-negative) and `command_interp_max_s` (0.10, positive); `ControlLoop` takes them by
  the same names plus `command_thread=False`, which writes each tick's command synchronously
  inside `step()` for tests. The trace keeps logging the submitted command per tick and gains a
  last column, `commands_written`, the command periods written so far (README *Command
  thread*).

### Changed

- **Disengage order.** `FollowerArm.disengage` releases the follower in this order: try
  `enter_gravity_comp_idle()`, then `zero_torque_mode()`; the hold fallback for a driver with
  neither stays. Behaviour is unchanged.
- **Seam blend.** Every chunk boundary after the first carries the last command into the new
  chunk: `offset = last command - first installed row` per arm, joints and gripper, added as
  `offset * (1 - i / seam_rows)` to the chunk's `i`-th row for `i < seam_rows`, measured on the
  ramped row so a boundary inside the start-up ramp is seamed too; the first chunk and the first
  after a reset stay the ramp's. `AppConfig` and `ControlLoop` gain `seam_rows` (default 8; 0
  disables). Nothing is logged per seam (README *Chunk handoff*).
- **Rate clamp.** Every command written to an arm is clamped to within `max_joint_step_rad`
  (default 0.02 rad per tick, 0.6 rad/s at 30 Hz) per joint and `max_gripper_step` (default
  0.05) of the previous command written to that arm; the first command is never clamped. One
  WARNING per burst (`command clamped: left joint 2 asked 0.130 rad in one tick, limit 0.020`)
  and `ControlLoop.clamp_count`. The last line of defence: the ramp, the seam and the policy
  keep steps well under the limit, so a clamp is a fault upstream.
- **Trace file.** `trace_path` (default null) names a CSV the loop appends one row per commanded
  tick to, `robots.control.TRACE_COLUMNS`: `t_s, chunk_id, row_index, ramp_alpha, seam_row,
  clamped`, the measured joints and grippers of both arms, then the commanded ones; opened in
  `__aenter__`, flushed every 30 rows, closed in `__aexit__` (README *Chunk handoff*).
- **Start-up ramp.** The first commands after start, and after every `DreamSessionExpired`
  reset, blend from the arms' measured joint positions and grippers into the policy's targets
  instead of arriving as a step change: `origin + alpha * (target - origin)`, `alpha` rising
  linearly over `max(ramp_s, largest joint delta / ramp_max_rad_s)` seconds sized from the
  chunk's first target, counted in commanded ticks so a stall or overrun stretches the ramp
  rather than skipping ahead in it.
  The buffer drains at the normal rate underneath. `AppConfig` and `ControlLoop` gain `ramp_s`
  (default 2.0) and `ramp_max_rad_s` (default 0.5), both positive floats; one INFO line
  announces each ramp with its duration and largest delta.
- **RealSense capture.** `cameras.RealSenseSource` reads an Intel RealSense colour stream
  through `pyrealsense2` (requested as `bgr8`, so nothing is converted on the station) in the
  `cv2.VideoCapture` read/release shape; `CameraReader` is unchanged. A `cameras` entry names
  its camera with `device` (cv2) or `serial` (RealSense), exactly one of the two: `CameraConfig`
  gains `serial: str | None` and `device` becomes `int | str | None`; `config.load` rejects both
  or neither by key name. `pyrealsense2` is not a dependency; RealSense stations
  `pip install pyrealsense2`, and a missing module is a `CameraError` that says so.
- **Frame windows.** The policy now receives, per camera role, the last `obs_window` frames
  (default 9, the base model checkpoint's `video_context_frames`) sampled every
  `max(1, round(fps / obs_fps))` captures (`obs_fps` default 5.0, the training video rate:
  every sixth capture of a 30 fps camera), oldest first, as `image_window.<role>`, the same
  list-of-base64-JPEG key as before and still the only image key (the older `image.<role>`
  singles are not sent; strict mode would reject them as undeclared). The capture thread keeps
  a per-camera ring of already-encoded frames and every published `Frame` carries a snapshot
  of it as the new `Frame.window` field, so a request re-encodes nothing and the tick path no
  longer touches cv2; until the ring is full the window is shorter, never empty, and a
  restarted reader starts a fresh one. `CameraReader` gains `obs_window`, `obs_stride` and
  `policy_image_size` (defaults 1, 1, None: today's single-frame wire) and the public
  `obs_stride` attribute; `CameraReader.from_config` takes `obs_window=`, `obs_fps=` and
  `policy_image_size=` as required keywords and logs the derived stride per camera (README
  *Policy frames*).
- **Policy image size.** Every sampled frame is downscaled to `policy_image_size` (new
  `AppConfig` key, `WIDTHxHEIGHT`, default `640x360`) with `cv2.INTER_AREA` before
  encoding; capture stays at each camera's `width` x `height`, and the example config now
  captures 1280x720 at 30 fps (a USB3 link per RealSense). `Frame.data` is still the full
  capture, for `loop.video`.

### Changed

- **JPEG quality is 85**, down from 92; `robots.cameras.JPEG_QUALITY` is a
  constant now, no longer an `encode_jpeg` parameter. `encode_jpeg(rgb, image_size=None)`
  takes the RGB pixel array and the optional `(width, height)` to downscale to, instead of a
  `Frame` and a quality.
- **`adapter.to_dream` no longer encodes.** It forwards `Frame.window` verbatim under
  `image_window.<role>` and raises `ControlLoopError` for a frame whose window is empty (only a
  hand-built frame can be). `robots.adapter` no longer imports `robots.cameras`.
- **cv2 is required on the capture thread.** The numpy BGR-to-RGB fallback for a missing cv2 is
  gone: the thread encodes the window, which needs cv2 anyway (a hard dependency), so a
  missing module now kills the thread with the `ImportError` in `CameraReader.error` instead of
  publishing frames the policy could never receive. The module still imports cv2 lazily.

## 0.2.0 - 2026-09-09

Moved to the serve wire that `dream` 2.0.0 forwards verbatim through DreamAPI (`POST
/v1/get_action`). The loop, the arms and the cameras are unchanged; what changes is what goes
across the seam, and what the config must say. Minor bump because the package is pre-1.0; the
config file and the `ControlLoop` constructor are not compatible with 0.1.0.

### Breaking

- **Key names are the serve's, not a modality config's.** Observation: `prompt`,
  `state.arm_r.joint_pos` / `state.arm_l.joint_pos` (float32 `[6]`, radians),
  `state.arm_r.gripper_pos` / `state.arm_l.gripper_pos` (float32 `[1]`), and
  `image_window.top` / `image_window.left` / `image_window.right`, each a list of one base64 JPEG
  (quality 92, BGR-encoded like `robots_wire.encode_frame_window`). Action: `q_r_chunk` /
  `q_l_chunk` of shape `[H, 7]`, six joints then the gripper; the serve's `q_r`, `q_l` and
  `per_key` are ignored. The `state.right_arm` / `video.*` / `action.*` names, the `[H, 1]` and
  `[H]` gripper shapes and the `*_grip` alias (`GRIPPER_ALIASES`) are gone.
- **Camera names must be the serve roles** `top`, `left`, `right`. `robots.run` raises
  `ConfigError` for any other name before hardware is built; `adapter.to_dream` raises
  `ControlLoopError` for one that reaches the seam.
- **`task` is a required top-level config field** (the language prompt) and `ControlLoop` takes
  it as a required keyword (`task=`). `adapter.to_dream(obs, task)` takes it as well.
- **`policy` may carry only `host`, `port`, `timeout_ms`, `strict`, `checkpoint` and
  `embodiment`.** `checkpoint` (str) is required; DreamAPI listens on `8000`. `dream` 2.0
  rejects any other key at `init` because the request has no field for it, and `robots.run`
  rejects it first, naming the keys. The example config's policy name and
  written-out embodiment block are gone.
- **`adapter.embodiment_spec(camera_names, horizon)`** takes the camera roles, not frame
  shapes: a JPEG window carries no declared size, so `image_window.<role>` entries are `{}`
  (presence only) and rotation no longer enters the block. The `action` group is keyed by bare
  names (`q_r_chunk`) with shape `[horizon, 7]`.
- **Refill error policy.** `DreamAuthError`, `DreamConfigError` and `DreamObservationError`
  now stop the loop (a retry fails the same way). `DreamSessionExpired` (DreamAPI replaced the
  session mid-episode) logs `episode restarted server-side` at WARNING, clears the buffered rows
  and refills. Every other `DreamError`, and a `ControlLoopError` from `adapter.from_dream`
  (wrong chunk shape, the same fault strict mode reports as `DreamActionError`), still costs
  one refill.

### Added

- `robots.cameras.encode_jpeg(frame, quality=92) -> bytes`: the one other cv2 call, used by
  the adapter; raises `CameraError` when cv2 is missing or the encoder refuses the frame.
- `robots.adapter.CAMERA_ROLES`, `robots.run.POLICY_KEYS`.
- `tests/test_end_to_end.py` now runs the real `dream` 2.0 client against a threaded HTTP fake
  of DreamAPI's `/v1/get_action` (sessions minted and echoed, refusals, restarts) and asserts the
  wire observation byte for byte: prompt, state lists, one JPEG per role that decodes back to
  the frame.

### Dependencies

- `dream>=2.0.0` (HTTP; `pyzmq` and `msgpack` are no longer pulled in through it).

## 0.1.0 - 2026-09-09

First release. The public inference control loop for a bimanual YAM follower setup: two i2rt
follower arms, one capture thread per camera, a fixed-rate `ControlLoop` that drains action
chunks, and `dream` as the policy client. Teleop, leader arms, DAgger and recording are not
shipped and not stubbed.

### Public surface

- `robots.config.load(path) -> AppConfig`: one YAML file builds everything; a missing required
  key, or an unknown key at the top level, in `follower_*` or in a `cameras` entry, raises
  `ConfigError` naming the key (`policy` is not checked because dream forwards it verbatim).
- `robots.followers.FollowerArm` (`from_config`, `read`, `write`, `hold`, `disengage`), the only
  module that imports i2rt, and lazily.
- `robots.cameras.CameraReader` (`from_config`, `start`, `stop`, `is_stale`, `is_alive`; the
  `frame` slot), the only module that imports cv2.
- `robots.control.ControlLoop` (`run`, `step`, the async context manager; `state` and `video`
  snapshots).
- `robots.adapter` (`to_dream`, `from_dream`, `embodiment_spec`), the only module that knows
  dream's key names.
- `robots.run.main(config)` and the CLI `python -m robots.run --config <file>`.
- The six data types in `robots.types` plus `ArmCommand`; the error hierarchy rooted at
  `RobotsError` (`ControlLoopError`, `ArmError`, `CameraError`, `ConfigError`).
- `robots.__version__`. `py.typed` shipped. `robots/__init__.py` exports nothing else; import
  modules (`from robots import control`).

### Decisions

- **The model is Dream-1.** Its checkpoints tolerate a query mid-chunk, so the prefetch path
  applies and `refill_at_remaining` is a per-checkpoint config value with default 0 (the sync
  path). The base model config's horizon is 48; it is the `action_horizon` config field, never
  hard-coded.
- **Units are radians.** i2rt reports joint positions in radians and the checkpoints were trained
  on them, so the loop's types carry `_rad` / `_rad_s` suffixes (`positions_rad`,
  `velocities_rad_s`, `commanded_rad`) and no conversion exists. The gripper is a float in
  [0, 1], 0 closed and 1 open (i2rt's mapper already normalizes it).
- **Key names come from the model's YAM modality config.** State `state.right_arm` [6],
  `state.right_gripper` [1], `state.left_arm` [6], `state.left_gripper` [1] (float32); actions
  `action.right_arm` [H, 6], `action.right_gripper` [H, 1], `action.left_arm` [H, 6],
  `action.left_gripper` [H, 1]; video `video.overhead`, `video.wrist_l`, `video.wrist_r`. Camera
  names in the config file are the keys after `video.`. The deployed checkpoint's `config.json`
  is the authority. (Superseded in 0.2.0 by the serve wire.)
- **Grippers are `[H, 1]` in the chunk**, because the serve returns per-key `(H, dim)` arrays.
  The adapter also accepts `[H]` and the `*_grip` alias. (Superseded in 0.2.0.)
- **Frames are RGB.** `Frame.data` is uint8 `[H, W, 3]` RGB; `CameraReader` converts from
  OpenCV's BGR at capture, and per-camera rotation (0/90/180/270) is applied before the size
  check.
- **`action_timeout_s` bounds the wait, not the call.** A refill started at `t0` is late once
  `now - t0 > action_timeout_s`. With an empty buffer the tick waits at most until that deadline
  and a late tick is a stall (hold the last command, log). A result that lands late is discarded
  and a fresh refill starts on the next due tick; one that lands in time fills the buffer.
  Nothing cancels the worker thread: dream has no cancellation, and its own `timeout_ms` bounds
  the call. A refill is due when `len(buffer) <= refill_at_remaining` and none is pending.
- **A late chunk is applied from its first action.** No fast-forward to elapsed ticks and no
  blending between chunks, decided for v1 rather than left open.
- **One config file, YAML.** `api_key` is a field of it, alongside the `policy` dict that goes to
  `dream.init` as-is. If `policy` lacks `embodiment`, `robots.run` fills it from
  `adapter.embodiment_spec`; if it is present and differs, `ConfigError`.
- **Packaging.** `robots/`, distribution `dream-robots`, depending on `dream` through a
  uv path source. i2rt is not on PyPI: the `hardware` extra pins it from git, and only
  `FollowerArm.from_config` imports it, so the core and the tests never need it.
