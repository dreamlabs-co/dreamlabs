# debug_scripts/

Operator scripts for a YAM station running the `robots` loop. They are not part of the `robots` package (nothing
imports them, tests do not cover them) and they touch the machine, not the code; each one says at the top when to
use it and what it does to the hardware. A station set up with `dreamcli setup` (README, *Command line*) runs the
agent with `dreamcli robot up` / `down` / `log` on `~/.dreamlabs/station.yaml`, without tmux; `station_run.sh` is the
form for a config kept elsewhere, and the other scripts take either file.

| Script | When | What it does |
| --- | --- | --- |
| `station_run.sh serve <config.yaml>` | every day: bring the station up | starts `python -m robots.station` in the `dreamrun` tmux session (a previous session is stopped first), log `~/robots-station.log`. The arms rest until a Start from the API (`:8091`) or the Playground's live view; see the README's *Station agent* |
| `station_run.sh start <config.yaml>` | a one-shot run without the agent | starts `python -m robots.run` in the same tmux session, log `~/robots-run.log`; motion begins as soon as the first chunk lands |
| `station_run.sh stop` | end either | Ctrl-C into the session (the loop's safe hold, or disengage after an `ArmError`), waits 2 s, kills the session |
| `station_run.sh home <config.yaml>` | before a run, or after one left the arms anywhere | runs `python -m robots.home` in the foreground: both arms interpolate to zeros with the grippers open over 3 s, then hold; refuses while a `dreamrun` session exists, because the loop's command thread and the home move must never write the arms at once (use the agent's Home instead) |
| `station_run.sh log` | watch | the last 40 lines of whichever log was written most recently |
| `identify_cameras.py [--out DIR]` | setting up a station, or after a camera was moved or replaced | headless: lists every camera the config could name, one line each (a RealSense by serial, with its model and USB link type; a UVC webcam by its `/dev/v4l/by-path` port, `usbv2-` aliases dropped), and writes one JPEG per camera into `--out` (default `/tmp/cams`) named by that identity, so the operator can see which camera is `top`, `left` and `right` and paste the identity into the config. Opens only cameras, one at a time; the arms are never touched. A camera that enumerates but cannot stream is reported with the reason, usually a USB2 link. What the Playground's YAM setup card tells the operator to run |
| `preflight.py <config.yaml>` | before the first run of the day, or after a camera or key change | read-only: loads the config, imports i2rt, prints each arm's zero-pose forward kinematics (`fk: left grasp_site at zero pose = [x, y, z] m`, about 0.25 m ahead of and 0.17 m above the base) with the configured speed cap, opens every camera through `CameraReader` and asks DreamAPI for two real inferences on those frames with a zero arm state; the arms are never opened, so nothing moves. Prints one line per check and `preflight done` |
| `bench_rollouts.py --record on/off [--seconds 120 --cameras 3 --width 640 --height 480]` | after changing the rollout recorder, or to size a PC for it | no hardware, but it uses cores: run it on a CPU box (`taskset -c 0-3` for a four-core PC). Runs the real `ControlLoop` over fake arms, fake cameras at a real frame rate and a fake dream client on the wall clock, with or without the recorder, and prints the tick time (p50 / p95 / p99 / max), the tick interval, the process CPU and memory, and the episode's size per minute |
| `hwmon_can_enable.sh [iface ...]` | a CAN link shows `ERROR-PASSIVE` / `BUS-OFF`, or i2rt cannot reach the motors although the arms are powered | bounces every `can*` link (or the ones named): down, up at 1 Mbit/s with `restart-ms 100` (auto-recovery from bus-off) and `berr-reporting on` (per-bit error frames for bus monitoring); the bus is down for ~100 ms, so run it only while nothing drives the arms. It prompts for the sudo password: `ip link set ... type can` needs root |
| `preflight.py <config.yaml>` | before every run, with the arms still off: a fresh config, a new key, a camera that was re-plugged, a gateway that moved | read-only: loads the config, imports the arm driver, starts every camera through the product's `CameraReader` and prints one line per camera (shape, frame age, mean brightness), then asks DreamAPI for two real inferences on those frames with a zero arm state and prints the latency and the first target. The arms are never opened; nothing moves. Needs the robots venv (`.venv/bin/python debug_scripts/preflight.py station.yaml`) |
| `station_run.sh start <config.yaml>` / `stop` / `log` | running the loop for real | starts `python -m robots.run --config` in a detached tmux session `dreamrun` logging to `~/robots-run.log` (survives the SSH session); `stop` sends Ctrl-C so the loop's own shutdown commands a safe hold before the session is killed; `log` tails the last 40 lines. A hand stays on the e-stop for the whole run |

Reading a link's state: `ip -details link show can_follower_l | grep "can state"`. A bounced link that goes
error-passive again as soon as the driver talks to it means the motors are not answering: check the e-stop and the
arm power supply before anything else.
