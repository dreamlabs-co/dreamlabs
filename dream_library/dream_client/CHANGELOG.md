# Changelog

All notable changes to `dream` are recorded here. The project follows
[Semantic Versioning](https://semver.org/); "public" means the surface listed under
*Compatibility promise* in `README.md` and nothing else.

## Unreleased

- `dreamlabs-client` 1.0.5 (2026-10-21): the release line and main carry one version number from here; no change to the library from 1.0.4.
- An arm file's chain may hold a continuous joint, and the file may name joints the robot holds still (2026-10-18, `dreamlabs-client` 1.0.2). A continuous joint, as a Vega-1's URDF writes its hand mount, was refused ("the chain takes fixed joints, and revolute and prismatic joints with limits"); it is now solved as a revolute one within [-pi, pi] at its URDF velocity (at most 3 rad/s), and the cut URDF says so, which pyroki needs. The new optional key `fixed` (`arm_file.FIXED_KEY`) lists chain joints to cut as fixed at their URDF zero, so the arm is the chain's other joints; a name that is not a moving joint on the chain is refused. `arm_file.TCP_CALIBRATION` names the setup tools' key.
- `dreamlabs-client` 1.0.0, the first major release (2026-10-19). The DreamAPI service serves this library from major 1: a request from a 0.x release is refused with `DA-4000 client_outdated`, and `pip install --upgrade dreamlabs` is the fix. No other change from 0.0.24.
- Comments and docs in the package's public files name Dream Labs' own code, design notes and tools by what they are, with no repository paths (2026-10-19, `dreamlabs-client` 0.0.23). Nothing else changes.
- `policy()` warns once, never refusing, when an arm file's tool center point is not one a person set on the real gripper (2026-10-18, `dreamlabs-client` 0.0.21): no `tcp_calibration` record (written by hand or by an agent), a skipped one, a `tcp`, `approach`, `jaw`, `base`, `flange` or URDF edited since it was set (the record's `digest`, `dream.arm_file.tool_digest()`), or `tcp` at the flange itself. A record from before the digest counts as set. The warning is one `UserWarning` line at the caller's line, once per arm file per process, and says to run `dreamcli tcp`; where warnings are errors it goes on the `dream` logger instead.
- `fine_tuning.create()` and `finetune()` document the service's learning-rate range as 1e-6 to 1e-4 (2026-10-18, `dreamlabs-client` 0.0.21; it was 1e-3, which blew up a real run).
### Changed

- The README, the design notes, the docstrings and the tests no longer name `dreamlabs/dream-1-yam`, which no environment serves since 2026-10-18 (2026-10-19, `dreamlabs-client` 0.0.23): the examples name `dreamlabs/dream-1-beta`, and a model with no EEF head is described as such. Wording only; no behaviour changes.
- The README, comments and docstrings describe the platform, the training service and the base models by what they are, not by internal file paths, repository names or tool names (2026-10-18, `dreamlabs-client` 0.0.22). Wording only; no behaviour changes.
- `ik.solve` defaults to `"traj"` (2026-10-19, `dreamlabs-client` 0.0.20): a control loop of your own that leaves `solve` out now runs the trajectory solve the robots stations run (`robots.config.DEFAULT_IK_SOLVE`), at dream-ik 0.3.1's velocity 5 / acceleration 50 with the pad that continues the chunk's motion (YAM, Unseen Task v3.2: 0.62 against `tick`'s 0.61 on the same scenarios). It compiles on a thread when `policy` opens and the first chunks are solved with `tick` until it is ready. `"solve": "tick"` keeps the row-by-row solve.
- With `ik.solve` `"traj"` and the `joint` head the client no longer compiles the trajectory solve (2026-10-19, `dreamlabs-client` 0.0.18): a joint head never solves a chunk, and the compile, 17-20 s on one slow CPU core, took CPU from the control loop. An `eef` head compiles it on a thread as before.

### Changed (breaking)

- Where the Dream Labs services are is read-only (2026-10-19): only your credentials say it (`~/.dreamlabs/credentials`, which the platform's pages print filled in for their own site; production when there is none), read once when a client is made, and nothing in a caller's code sets or changes them. `DreamClient()` takes only `api_key` (its `data_url`, `platform_url` and `gateway_url` arguments are gone), `LiveViewClient` lost `platform_url`, every `dream.datasets`, `dream.fine_tuning` and `dream.models` function lost `host`, and `DreamClient.policy()` refuses the config keys `host`, `port` and `scheme` with `DreamConfigError`, where a key the config set had won over the credentials. `repr(DreamClient())` names no address. `dream.credentials` is no longer part of the public surface: the reference does not document it.
- The reference pages carry no "Generated from the docstrings of ..." footer.

- Docs only (2026-10-18, `dreamlabs-client` 0.0.6): the README and the fine-tuning docstrings no longer state a step count or a batch size, say that `get_datasets()` finds a lost dataset id, and describe `cancel()` and `delete_dataset()` as priced fine-tuning has them: a job runs to its end once queued.
- Comments, docstrings and changelog entries in the package's public files name no internal people, trackers, hosts or repositories (2026-10-18, `dreamlabs-client` 0.0.11). Nothing else changes.
- With `ik.solve` `"traj"`, the rows the client pads a chunk back to its length with continue its last motion instead of holding its last pose (2026-10-18, `dreamlabs-client` 0.0.16): the trajectory solve sees the whole chunk, so a hold braked the rows before it (a YAM eval: the last ~10 executed rows at ~70% of the plan's speed). The vendored dream-ik 0.3.1 solves `traj` with lighter velocity and acceleration weights (5 / 50, from 20 / 100), which no longer brake the arm at each chunk's end or slow its answer to a correction, and runs no hard fences by default (`ServeSpec.fences`): an `ik.region` is clipped targets and a cost, without the hold. `"tick"` is unchanged.
- Comments, docstrings and changelog entries in the package's public files name no internal people, trackers, hosts or repositories (2026-10-18, `dreamlabs-client` 0.0.16). Nothing else changes.

- The `ik` config takes `solve` and `region` (2026-10-18, `dreamlabs-client` 0.0.4). `solve`: `"tick"`, row by row, the default and unchanged, or `"traj"`, the whole chunk in one solve with joint velocity, acceleration and jerk costs that continues the arm's last three commands (dream-ik 0.3.0). `region`: a keep-inside box per arm, `{side: {"lo": [x, y, z], "hi": [x, y, z]}}` in the arm's base frame, null for an open face; the hand targets are clipped inside it and a row that leaves it holds the arm. Neither key, nothing changes.

- Where fine-tuning is priced (2026-10-18): `fine_tuning.cancel()` is refused with `conflict`, since a job runs to its end once queued and what it costs is settled by how it ends; `delete_dataset()` raises `conflict` while a job is queued or running on the dataset; `fine_tuning.create()` and `finetune()` raise `payment_required` when the account's credits do not cover the price. Where it is free, all three work as before.

### Fixed

- `dream.LiveViewClient` redials within 2 s when its link's network path goes dead (2026-10-18). Closing such a link sends a close frame behind bytes the relay never acknowledges, and websockets waits for them with no deadline, so the client sat on the dead link until the kernel's TCP timeout (about 15 minutes) with Live View showing the robot offline: seen on a Maker Arm whose Wi-Fi dropped while its Ethernet came up. Every close of the link is now bounded (`_LINK_CLOSE_S`) and the socket aborted past it.
- A robot whose parts marked not trained make its `state` or `action` wider than 128 values now registers with `add_embodiment` (2026-10-17): only the parts that train count against the cap, and a fine-tune's state against the base's 64 (`shared.datasets.embodiments.trains()`). The refusal names the trained count: "The state trains 67 values (the dataset has 67); at most 64 can."
- A model trained on YAM arms runs on an SO-101 (or any arm with a gripper drive) whose embodiment names no gripper part (2026-10-16). An SO-101 station's embodiment, registered by the robots setup wizard's New before the gripper fix added `<side>_gripper`, was refused at every start with `config key 'embodiment' must name one gripper part of the right arm beside [...], got []`, though such a model never reads the drive: the client sends it the grip as `state.<side>_gripper`. `client_ik._drive_key` now asks for the part only when the model reads it; a fine-tune of the robot still needs exactly one, and a body naming two is refused for any model.

### Added

- The `policy()` config key `robot`, `"yam"` or `"other_embodiment"` (2026-10-19, `dreamlabs-client` 0.0.24), sent with every `get_action` as the observation key `embodiment` (not the config key `embodiment`, the embodiment config, which is never sent). `"other_embodiment"` says the arm is not the one the model's state is from: a Dream-1 base model then reads none of the request's state (the joints, each hand's pose and the grip are withheld: the model is given zeros in its own scaled units in place of them, an input it was trained on half of the time) and acts on the cameras and the prompt. Its tool poses are still anchored on the hand pose the request carries, so that pose is still sent, the TCP's, absolute, in the arm's base frame, and it answers no joints: `per_key["action.<side>_arm"]` is null. `"yam"` says the joints are the model's own (a YAM, or the robot a fine-tune was trained on), and the state is read as sent. Left out, `ik` on an arm that is not a YAM with a model trained on YAM arms sends `"other_embodiment"`, where the model had read YAM's joint slots as zeros beside the arm's own hand pose and grip; with head `eef`, `q_r_chunk` and `q_l_chunk` are solved from the tool poses as before. Anything else sends nothing, as before. A `robot` you set always wins, so a loop on its own IK (no `ik`) on such an arm sets `"robot": "other_embodiment"` and keeps sending six zeros as each `state.<side>_arm`, the grip and its own FK's hand poses; no `q_r_chunk` or `q_l_chunk` is packed from the null joint answer. Any other value is a `DreamConfigError` at `policy()`, and an observation that carries `embodiment` itself is a `DreamObservationError`. A fine-tune reads the state as it was trained to, whatever `robot` says. README, *EEF checkpoints and client IK*.
- `dream.LiveViewClient`'s tick guard watches the client's own thread, never the caller's loop (2026-10-18): the client reads the newest stream() on its own niced thread 60 times a second and pauses the video only when that thread's p95 poll interval passes two poll periods (33 ms) for 2 s while a run is on, the computer having no CPU to spare. It had compared the spacing of the caller's stream() calls with a baseline from the run's first 10 calls, so a loop of one's own calling it from its policy thread (a Maker Arm's, seen on 2026-10-18) paused its video on its own jitter and its first get_action(), though nothing the client did had slowed it. stream() may be called from any thread at any rate.
- `dream.LiveViewClient` does everything the station's Live View did (2026-10-18), since the station now runs it (it was `robots.live.LiveAgent`, ported unchanged): `stream()` takes optional `arms` (the page draws the robot from them), `error` (the banner for why the arms are not moving), `prompt`, `run`, `model` (`(checkpoint, action_space)`) and `steps`; `register_callback(fn, home=True, reset=True, prompt=True)` takes the page's Home, Reset arms and new tasks (`EventChange.home`, `reset`, `prompt`), and a callback may return the state, `{"state", "error"}` or an awaitable, which the client waits for up to 10 s and never cancels halfway for a Start, Stop, Home or Reset; `model_fixed=False` opens the page's model pickers (`get_model()`, `get_steps()`); `cameras=` names the cameras up front; `face_blur` (on by default) blurs every encoded frame; `stats()` returns the link's counters; and `dream_client` is an attribute, for a loop that opens a new `DreamClient` per run. A frame is encoded once: hand the client a new image per camera frame. The client records nothing; the run's `DreamClient` records it.
- `DreamClient.checkpoint` (2026-10-18): the model the open policy runs, None before `policy()` and after `close()`. `LiveViewClient` reports it to Live View and marks the robot's model as fixed (`status.model_fixed`), so the page shows the model your code runs and locks its model and action pickers, which it had offered though a model picked there never reached the loop.
- `dream.LiveViewClient(..., dream_client=client)` (2026-10-18): given the loop's `DreamClient`, the client reports the model's round trips (`last_timing`) to Live View while the status is `running`, at most every 2 s, as the station does; without them the page showed a running robot as "Dream-1 is getting ready" for the whole run. A refused link (4001, 4004, 4005) now waits its 30 s backoff while the loop keeps streaming, where it had redialed at the frame rate.
- A robot's part may be marked not trained (`{"kind": "not_trained"}` in `parts`, 2026-10-17; `shared.datasets.embodiments.KINDS`): `add_embodiment` registers it, and on a fine-tune of that robot `get_action` takes the part in the observation like any other but sends none of it and answers no target for it, so the robot holds it itself.
- `finetune` and `fine_tuning.create` take `lr_schedule`, `"constant"` or `"cosine"` (2026-10-17): cosine warms up as constant does, then decays the learning rate to 0 by the last step. None (the default) sends nothing, so the service trains `"constant"`, every job's schedule before, and a call that leaves it out sends exactly what it did; another word is refused by the service with `invalid_request` naming the knob. The docstrings say cosine decay works best for specialization and that specialist tasks may not be highly reliable yet.
- A fine-tune of a robot whose action part records deltas (`"delta": true`) answers in deltas (2026-10-17; `shared.datasets.conversion.from_targets`): the model predicts that part's targets, and `get_action` returns the change each row makes, the first from the observation's `state.<part>` and each later one from the row before. An earlier client refuses such a robot's config at `policy()` (`DreamConfigError`), never running it.
- `validate_dataset()` and `upload_dataset()` now read every video's format with FFmpeg (through PyAV) and refuse a dataset the service would refuse, before anything is uploaded: a video that is not H.264, HEVC, AV1 or VP9 in MP4, or that carries a subtitle track, fails the check with the service's own line, e.g. `Directory 's': videos/chunk-000/observation.images.top/episode_000003.mp4 is video in format 'mp4v'; accepted: H.264 (avc1), HEVC (hev1, hvc1), AV1 (av01), VP9 (vp09) in MP4.` The `datasets` extra now installs `av` (`>=15`, the `live` extra's floor).
- `ik` arm `yam` with head `eef` runs any YAM model (2026-10-16): with `strict`, a reply's tool poses and grips are not required, and a reply with none (a model with no EEF head, `dreamlabs/dream-1-yam`) runs its joint chunks as they come, as head `joint` would, with one warning per session naming the model (`dream.client_ik`). A reply with tool poses is solved as before.

### Fixed

- `upload_dataset` checks the temporary directory has room for the zip before writing it (2026-10-16). The zip is stored uncompressed, about the dataset's size, so a dataset larger than the free space (5.55 GB against 5.5 GiB) failed part way through writing it. It now raises `DreamConfigError` naming the directory, the space needed and the space free, and saying to set `TMPDIR`; nothing is registered.
- A `meta/info.json` without a field the checks need is refused naming the field (2026-10-16): one without `chunks_size` was refused only as "not a LeRobot v2.1 info file". The required fields are `codebase_version`, `fps`, `chunks_size`, `total_episodes`, `total_frames`, `data_path`, `video_path` and `features`, with `action` and `observation.state` in `features` (`shared.datasets.validation.REQUIRED_INFO_FIELDS`, `REQUIRED_FEATURES`).
- `policy()` refuses a fine-tune of a robot registered with `parts` when the platform withholds those parts (2026-10-16): the platform lists them only to the account that registered the robot, on a client that converts them, so another account's run (a shared, domain-granted or public fine-tune) could not convert and would have sent the robot's own part names. With `strict` on it is now a `DreamConfigError` at `policy()` naming the checkpoint and its robot and saying to pass the robot's config as `config['embodiment']` or to run it from the owning account on the current client; `Model.parts_withheld` (new, False from an older platform) says so. The client's platform calls (`dream.datasets`) now carry `User-Agent: dream-client/<version>`, by which the platform tells a client that converts.
- DreamAPI refuses a checkpoint whose robot has `parts` to a client older than 4.1.0, this one (2026-10-16): `DA-4000 client_outdated`, saying to upgrade the client. An older library, whatever its `strict`, sent the robot's own values in the slots the model trained on. A request without the version header (curl, a source checkout's `0+unknown`) is refused on such a checkpoint too; every other checkpoint is served as before.
- With `strict` on, a `checkpoint` that `get_models()` does not name raises `DreamConfigError` at `policy()` (2026-10-16; a checkpoint missing from `GET /v1/models`): it ran unchecked, and a robot with `parts` unconverted. Every deployed gateway refuses such a checkpoint to the key anyway (it serves a key what the listing shows), so the client now says so first, by name, before anything is sent.
- With `strict` on, a model lookup that fails at `policy()` raises `DreamProtocolError` (2026-10-16): it warned and ran unchecked, and a robot with `parts` unconverted, its gripper in the trained 0-1 grip, whenever `GET /v1/models` failed (a platform restarting during a deploy). Nothing opens and nothing is sent; call `policy()` again. `strict: False` still skips the lookup and sends unchecked.
- A `get_action` whose reply is cut after the gateway started answering is not sent again (2026-10-16): a reset while the reply's body was read counted as a stale keep-alive, so the client re-sent the request and the gateway ran (and billed) it twice. It is now `DreamProtocolError`; a kept-alive connection the gateway closed before answering is still retried once on a fresh one.
- With `ik` arm `yam` and `strict`, the YAM's own embodiment block passes (2026-10-16): the poses and grips the client adds (`state.<side>_eef_xyz`, `_eef_rot6`, `_grip`) are read too, where they were refused as keys the block does not declare, and `action.<side>_gripper` is not required, since a Dream-1 base model answers its gripper as `action.<side>_grip` and the serve packs either into the joint chunks. A YAM station now sends the same config for every model (`robots.run.policy_config`).

### Changed (breaking: 3.0.0)

- Removed: the `steps` argument of `finetune` and `fine_tuning.create` (2026-10-16). Every job trains 500 steps, fixed for now, and the service refuses a request naming another number, so a call passing `steps` raises `TypeError`. The docstrings say the batch sizes are 8, 16, 32 and 64 (the service refuses 24, which the base cannot split), and the README's training time is the measured one: about 4 to 5.5 hours for 500 steps on two or three cameras.
- `policy()` checks calls to shared and public fine-tunes of a custom body too (2026-10-14): it loads the body's embodiment config from the model itself (`Model.embodiment_config`, new, from the platform's `GET /v1/models`), whichever account registered the body. It looked the body up in `get_embodiments()`, which lists only bodies your account holds, so such a fine-tune (a company running one whose body Dream Labs registered) loaded no config, without a warning, and its calls went unchecked. Now, with `strict` on (the default), a call those checks refuse (a missing camera, a part of the wrong width, an extra `state` key) raises where it used to be sent; pass `strict: False` to send unchecked as before. A platform from before this change answers no `embodiment_config`; its models read None there and run unchecked, so a station on this library still starts against it. A listed config this library's parser refuses (a key a later platform lists) is a `DreamConfigError` at `policy()`.
- `dream.DreamClient` keeps the camera window itself, and that is now the only way to run a model (2026-10-14). Call `set_observation(frames, observation, *, timestamp=None)` on every camera tick, with one base64 JPEG frame per window key (`video.<role>` for a fine-tuned model, `image_window.<role>` for `dreamlabs/dream-1-yam`) and every other key the model reads (`state.*`, `prompt`), and ask for the next chunk with `get_action(*, commanded=None)`, which takes no observation. The client keeps one tick's frames every `1 / obs_fps` seconds of the caller's timestamps (the tick nearest each due time, so 30 Hz ticks keep exactly every sixth at 5 fps and a pause restarts the schedule), holds the last `obs_window` per key, and sends them, oldest first, with the newest observation; the checks, pacing, seam smoothing, session and errors are as before. `policy()` takes `obs_window` (default 9) and `obs_fps` (default 5), consumed locally and never sent, and now returns None. The client carries what the policy object did: `reset_episode()` (ends the session and empties the window), `refill_due(executed, remaining)`, `execution_horizon`, `action_hz`, `mode`, `last_timing`, and the new `session_id`. set_observation() never waits on a get_action() running on another thread or on the network; two get_action() at once are refused.

- `validate_dataset()` and `upload_dataset()` refuse a dataset whose videos are not at LeRobot v2.1's standard `videos/chunk-<NNN>/<video key>/<episode>.mp4`, naming the first file and the layout, instead of reporting a wrong number of video streams; and a `meta/info.json` whose `video_path` is missing or is not that layout's template, or that names a video an episode does not have (checked per episode and video key, as the parquets are). An mp4 at any depth under `videos/`, a flat `videos/<key>/<episode>.mp4` included, is held to the layout. Fine-tuning reads that layout only.
- Seam smoothing joins each chunk with a velocity blend instead of a crossfade. From the row the loop installs the chunk at (the round trip times `action_hz`), the 16 rows after it start exactly where the arm's current motion goes next, carry its velocity, hand it over to the new plan's and land exactly on the plan; before, the head of the chunk was a smoothstep crossfade of positions from the old plan to the new one, which left a velocity bump at every seam. The Savitzky-Golay filter now runs at twice the row rate with a window of 11 and filters every column, the gripper's included. An arm holding at the end of its plan (sync pacing) starts from rest; the first chunk of an episode and an arm off its plan are still filtered only. Still always on with no setting; what `get_action` returns is the same keys and shapes.

- The missing-dependency hint off production (pyarrow or boto3 not installed, the credentials naming any platform but the built-in one) is now the line that fetches and installs that platform's current build with the api key, `curl -fOJ -H "Authorization: Bearer $DREAM_API_KEY" <platform>/downloads/latest && pip install ./dream-*.whl`, instead of sending the user to sign in and download from the Fine-tuning page. The production pip line is unchanged.

- The missing-dependency hint (pyarrow or boto3 not installed) no longer says `pip install "dream-client[datasets]"`, which is not how the library is installed. On production (the credentials name the built-in platform URL) it is a pip line whose package name is provisional, since none is decided yet; anywhere else it names the configured platform's Fine-tuning page, which offers the library's wheel to a signed-in user. Both live in one place, `dream.datasets`.

- The tuning constants of `dream.datasets` (`TIMEOUT_S`, `ATTEMPTS`, `BACKOFF_BASE_S`, `BACKOFF_MAX_S`, `PART_BYTES`, `TRANSFER_CONCURRENCY`, `ERROR_LINE_MAX`) are private (`_TIMEOUT_S` and so on): they were never part of the compatibility promise.

- `reset_episode()` and `close()` release the held session on the gateway with one `POST /v1/end_session` (a two-second, best-effort request, swallowed on any failure), so a stop or a new episode frees its seat now instead of after the gateway's idle eviction; before, both were local and the seat lingered. Before the first request, or twice in a row, they still send nothing.

### Added

- Strict mode reads an embodiment config. `embodiment` in the config of `dream.init` (and `DreamClient.policy`) may now be the embodiment config a body was registered with (`state` and `action` parts with their `[start, end)` spans, `video` roles), as well as a shape spec: the client checks that every observation carries `state.<part>` as wide as each state part and `video.<role>` as a frame window (a non-empty list of base64 JPEG strings) for each camera role, and no other grouped key, before anything is sent; and that every reply's `per_key` carries `action.<part>` rows of each action part's width, the same number of rows each (a width-1 part may come back flat), before it is returned. This is the contract a checkpoint fine-tuned on that body reads. The two forms cannot be confused (every entry of a spec is a dict; a config's are spans and video keys), so every shape spec keeps its meaning, the YAM station spec included; a config the parser refuses is a `DreamConfigError` at `init` with the parser's line. Accepting a value that was refused before is a minor bump.

- `DreamClient.policy()` loads the embodiment config of one of the account's fine-tunes (the model's `embodiment` id matched against `get_embodiments()`, once per checkpoint) and keeps it for the session, so every `get_action()` checks the observation against the body's config before anything is sent. An explicit `embodiment` or `strict: False` skips the lookup; a public model, or a lookup that fails (with a warning), leaves the checks off as before. `Embodiment` gains `id`.

- `dream.DreamClient`: one object for the whole fine-tuning-as-a-service lifecycle and inference. It carries the account's key and the three hosts (from the credentials, overridable per client) and forwards to the modules below: `add_embodiment` / `get_embodiments`, `validate_dataset` / `upload_dataset` / `get_dataset_status`, `finetune` / `get_finetuning_status`, `get_models`, and `policy` / `get_action` (the inference client `dream.init` returns, opened and forwarded to, unchanged). The module functions stay usable on their own; `DreamClient` is the documented primary surface, and the README's *Fine-tuning as a Service* section and `examples/faas_tutorial.ipynb` walk it end to end. A new public class is a minor bump; `dream.init` and its object are unchanged.

- `dream.models`: `list_models()` over the platform's `GET /v1/models`, the checkpoints an account may run (the public ones and its own fine-tunes), each a `Model(id, owner, base_model, embodiment, servable, created_at)`; a row is `servable` once DreamAPI holds its weights, and `id` is what `policy` (or `dream.init`) names as `checkpoint`. The platform is a different host from the data service (`DREAM_API_URL`).

- `dream.fine_tuning`: fine-tuning jobs on the Dream Labs data service, beside `dream.datasets` and on its wire (the same `host` and `api_key`, the same errors). `create(dataset, suffix, *, steps=None, learning_rate=None, batch_size=None)` queues a job on one of the account's `processed` datasets (`POST /v1/fine_tuning/jobs`; the three knobs go together: none sends no `hyperparameters` and the service applies its recipe defaults, all three are sent whole, some but not all is a `DreamConfigError` before anything is sent), `list()` and `get(job_id)` read the account's jobs, `cancel(job_id)` cancels one, and `queue()` reports the line; each answers the service's JSON as it came, a job as a `dict` (`id`, `dataset`, `embodiment`, `base_model`, `suffix`, `fine_tuned_model`, `status`, `hyperparameters`, `queue_position`, `created_at`, `finished_at`, `error`). Once a job is `succeeded`, `dream.init({"checkpoint": job["fine_tuned_model"]})` calls the model; the first `get_action` is refused `DA-2000 pool_warming` while DreamAPI stages the weights and boots a serve. A refusal by the service is a `DreamServerError` with the service's `code` (`not_found`, `conflict`, `invalid_request`). A new public submodule is a minor bump; `dream.init` and its object are unchanged.

- `dream.datasets`: embodiments and datasets on the Dream Labs data service. `add_embodiment` records a robot body as `<username>/<name>` plus one config the user writes (`state` and `action` parts with their `[start, end)` spans, `video` roles to the dataset's video keys), parsed locally (`shared.datasets.embodiments`, carried in the wheel) before it is sent, and `list_embodiments` lists the caller's own; `validate_dataset` runs the dataset checks (`shared.datasets.validation`, also in the wheel) on a local directory against a config and answers a `Report`, with no key and nothing sent; `upload_dataset` fetches the embodiment's config, validates, writes the dataset as one uncompressed zip in the temporary directory, registers it with the zip's size and the episode count, sends the zip straight to S3 with boto3's transfer manager on temporary credentials the service answers for that one object, completes, and answers the `ready_to_process` dataset the service checked; the service's pipeline then takes the dataset through `processing` to `processed` (or `failed` with its one line), and a name whose dataset is `ready_to_process`, `processing` or `processed` is taken; whatever fails after the registration is reported to the service (`fail`, the dataset is `failed` with that line) and raised, and the name is reused by the next run. `get_dataset(dataset_id)` reads one dataset's status as the service holds it now. A host left out now defaults to the credentials' `DREAM_DATA_URL` (before, a data-service call refused a missing `host`); a key left out is still the credentials'. Hidden files (a `.DS_Store`) are neither checked nor sent. Two new errors in `dream.errors` (not the `dream` namespace), `DreamDatasetError` (the local checks refused the dataset) and `DreamUploadError` (the zip could not be written, the transfer did not finish, or the service refused the completion). The checks open parquets with pyarrow and the upload needs boto3, a new optional extra: `pip install "dream-client[datasets]"`. A new public submodule is a minor bump; `dream.init` and its object are unchanged.

- `dream.credentials`: the credentials file `~/.dreamlabs/credentials` (or the file `DREAM_CREDENTIALS` names), four lines a shell could `source`: `DREAM_GATEWAY_URL`, `DREAM_API_URL`, `DREAM_DATA_URL` and `DREAM_API_KEY`. `dream.credentials.load()` resolves each name from the environment, else the file, else the built-in default, and `dream.init` takes its `host`, `port` and `scheme` defaults from the gateway URL and, when no `api_key` is passed, the key from the record; `DreamClient` takes the data service and the platform from the same record. So `dream.init({"checkpoint": ...})` alone reaches the hosted gateway with the account's key, and moving a machine to another environment is editing that one file rather than every config on it. A key the config sets still wins, key by key, and an `api_key` argument wins over the record. A malformed URL is `DreamConfigError` at `init` naming the variable and, when it came from the file, the file; empty is unset; a missing file is the defaults. The three variable names were introduced for the environment in the same unreleased span; the file is where they now live.

### Changed

- Seam smoothing between consecutive chunks, always on: `get_action` now filters each `q_r_chunk` / `q_l_chunk` and blends it into the plan the arms are already on before returning it, so the control loop's swap from one chunk to the next carries position and velocity over instead of stepping. The client uses only what it already holds: the observation's `state.<arm>.joint_pos` finds the row of the previous chunk the arm is on; a Savitzky-Golay filter (7 rows, order 3) removes per-row jitter with the previous plan as left context; and the head of the chunk crossfades from that plan under a smoothstep weight over a seam sized from the measured row rate and round trip (the rows the loop executes while a chunk is in flight, plus four, never fewer than four or more than half the chunk). There is no config key, environment variable or argument for it: the numbers are the library's. Not blended: an arm more than 0.5 rad from every row of the previous chunk, the first chunk of an episode, and the first after `reset_episode()` or a session replaced mid-episode. The gripper column and every other action key are the serve's values, and the wire is unchanged. A chunk is no longer returned row for row as the serve sent it, which changes what a caller sees without changing any signature: a minor bump.
- The built-in gateway is production's, `https://api.dreamlabs.ai`, where before it was a preview gateway. A process that named no gateway anywhere now reaches production; any other site is named in the credentials file, which its platform's setup card prints. This changes where an unconfigured client sends its requests, so it is a minor bump, as 2.5.0 was.

### Fixed

- No exception outside `DreamError` escapes a public call any more, as `dream.errors` has always promised. A value JSON cannot carry in an observation (bytes instead of a base64 string, a set, an object array, a key that is not a string, a structure that holds itself) is now `DreamObservationError` naming the key, raised before anything is sent; it was a plain `TypeError` (or `ValueError`) from the encoder, so code that caught `TypeError` there must now catch `DreamObservationError`, which is a `ValueError`. A `gateway_url` passed to `DreamClient` whose port is not a number in 1..65535 (or that is no URL) is now `DreamConfigError` naming the URL, from `policy()` and from `dream.credentials.gateway_parts()`; it was a plain `ValueError` from `urllib`. The same sweep turned these into Dream errors too: a ragged list under a shape strict mode checks (`DreamObservationError`); without strict mode, a reply with no action dict or a chunk that is not rows of numbers (`DreamActionError`; it was a `TypeError` or `ValueError` from the chunk blending); an API key holding a line break or a character outside Latin-1 (`DreamConfigError`, whose message never shows the key; it was a `ValueError` holding the whole header, or a `UnicodeEncodeError`); a host name with a space, an empty label or a bad port, in the inference config or in a data or platform URL (`DreamConfigError`; it was an `InvalidURL`, a `UnicodeError` or a `ValueError`); an answer of the wrong shape from the data service or the platform (`DreamProtocolError`; it was a `KeyError`, `TypeError` or `ValueError`); a fine-tuning knob JSON cannot carry, such as a numpy number, and an embodiment config keyed by something other than strings (`DreamConfigError`); a dataset path that cannot be listed or holds a NUL byte (`DreamConfigError`), a dataset file that cannot be read (a failing `Report` line, so `DreamDatasetError` from the upload; it was a `PermissionError`), and a dataset file dated before 1980, which a zip cannot record (`DreamUploadError`); a credentials file that is not UTF-8 text (`DreamConfigError` naming it). A measured joint pose that is not numbers no longer fails the call: that arm's chunk is filtered but not blended into the previous one. `tests/test_only_dream_errors.py` pins each.

- `DA-4000 BAD_REQUEST` is raised as `DreamBadRequest`, a `DreamConfigError` (so every `except DreamConfigError` still catches it and the control loop still stops on it) that is also a `DreamServerError` with `code` and `reason`. Before, the refusal came back as a bare `DreamConfigError` with the envelope folded into the message, so a station could not tell an unknown checkpoint from a body too large except by reading the text, and the live view reported the failure as a station config fault when the operator had picked a checkpoint DreamAPI does not know.

## 2.0.0 - 2026-09-09

Re-pointed from the `/inference` ZMQ envelope to DreamAPI as built: `POST /v1/get_action` over
HTTP. Major bump per the versioning table (wire format break, changed error semantics, changed
config contract). The public surface (`dream.init`, `get_action` / `reset_episode` / `close`, the
error type names, `__version__`) is unchanged in shape; what changes is what goes in and what
comes out.

### Breaking

- **Transport.** One keep-alive HTTP connection per client, `POST /v1/get_action` with a JSON
  body `{checkpoint, session_id, reset: false, observation}`; numpy arrays are sent as JSON
  lists. ZMQ REQ/REP and msgpack are gone. The default `port` is now `8000` (DreamAPI's
  listener), not `5555`. The credential travels as `Authorization: Bearer <api_key>`, not as an
  `api_token` body field.
- **Status envelope.** Every reply carries DreamAPI's `status {code, name, reason, retryable,
  retry_after_s, trace_id, detail}`; the client maps the `DA-xxxx` codes to exceptions.
  `DreamServerError` gained `reason`, `retryable` and `retry_after_s` attributes alongside
  `code`; `code` is the envelope code (`"DA-2000"`), never a bare-string error. A reply without
  an envelope is `DreamProtocolError`.
- **Config keys.** `checkpoint` (non-empty `str`) is required and is the one config value sent
  to DreamAPI. `embodiment` is read locally and never sent. **Every other key is a
  `DreamConfigError` at `init`**: DreamAPI's request has no config field, so nothing can be
  forwarded. `policy`, `temperature` and the rest of the "opaque blob" no longer exist.
- **Observation and action keys.** The observation is the serve's own dict: `state.<slot>.<field>`
  float32 arrays, `image_window.<camera>` lists of one base64 JPEG, `prompt`. Actions come back
  as the serve returns them: `q_r_chunk` / `q_l_chunk` of shape `[H, 7]` (gripper as the seventh
  column) plus whatever else the serve adds, which strict mode tolerates. The `action` group of
  `embodiment` is keyed by bare action names (`q_r_chunk`), not `action.<key>`. Ungrouped
  observation keys (`prompt`) are not checked; list values are shape-checked only.
- **`options` is unsupported.** `get_action(obs, options=...)` with anything but `None` raises
  `DreamConfigError` before sending: the request schema has no field for it.
- **Session loss is an exception, not a silent retry.** `DA-0001 OK_NEW_SESSION` with a
  `reason` other than `new` on a request that carried a session id raises
  `DreamSessionExpired`; the new session is adopted, the action that came with it is not
  returned, and every replacement is reported. The 1.x "drop the id and retry once" is gone: a
  replaced session means the episode restarted server-side, which only the caller can judge.
- **`reset_episode()` no longer reconnects.** It drops the session id only; the next request
  carries `session_id: null` and DreamAPI mints a session with a forced reset. The connection is
  kept.
- **`DreamConfigError` from the server** now means `DA-4000 BAD_REQUEST` (malformed request,
  too large, invalid session id), carrying DreamAPI's `detail` verbatim; `invalid_config` no
  longer exists. `DreamAuthError` is `DA-1000`. `DreamProtocolError` now also covers a refused
  connection (it surfaces at once, not as a timeout).
- **Dependencies.** `numpy` only. `pyzmq` and `msgpack` are dropped; the transport is
  `http.client` and `json` from the standard library.

### Added

- One transport-level retry: a request that fails to send on a reused keep-alive connection
  (the gateway closed it idle, or restarted) is sent once more on a fresh connection. Nothing
  was processed the first time; a second failure is `DreamProtocolError`.
- `TCP_NODELAY` on the connection, so a request is not held for the peer's delayed ACK.

## 1.0.0 - 2026-09-09

First release. A standalone client for DreamAPI's `/inference` gateway, derived from the GR00T
policy client's socket, timeout-recovery and close code.

### Public surface

- `dream.init(config, api_key)` is the only constructor. It does no network I/O; the session
  opens on the first `get_action`.
- The client exposes exactly `get_action`, `close`, and the context manager. `dir(client)`
  shows nothing else.
- Error hierarchy rooted at `DreamError`: `DreamConfigError`, `DreamObservationError`,
  `DreamActionError`, `DreamTimeout`, `DreamProtocolError`, `DreamServerError`,
  `DreamAuthError`, `DreamSessionExpired`.
- `dream.__version__`, asserted against package metadata in the test suite. `py.typed` shipped.

### Decisions worth knowing when porting from the GR00T client

- **`get_action` returns the action dict only.** There is no `(action, info)` tuple; DreamAPI
  does not produce `info`, and an always-empty dict invites someone to start filling it.
  Callers that unpacked a tuple must change.
- **`strict` defaults to on.** Observations are validated against the non-`action` groups of
  `config["embodiment"]` before they are sent, and actions against the `action` group before they
  are returned: keys, shape and dtype, never values. Validation is local and free; with no
  `embodiment` in the config it is a silent no-op.
- **One endpoint.** Every request goes to `/inference`; there is no `endpoint` field on the wire
  and no endpoint namespace in the client. New capability arrives as a config or `options` field
  understood server-side, never as a new method.
- **Removed:** `kill_server`, `ping`, `reset` and `get_modality_config`, together with the
  `BasePolicy` base class. The client neither controls the server's lifecycle nor holds a
  policy; it is a caller of a hosted one.
- **Session retry, once.** When DreamAPI answers `unknown_session` or `session_expired`, the
  client drops its id and re-sends the identical request with `session_id: null`. A second
  session error raises `DreamSessionExpired`. This is the only retry the client performs;
  timeouts, protocol errors and other server errors are raised straight to the caller.
- **The config is the user's dict.** `host`, `port`, `timeout_ms` and `strict` are consumed
  locally and type-checked at `init`; every other key is forwarded byte-identical on every
  request. Unknown keys are forwarded, not rejected. The API key is a separate argument and
  never part of the config.
- **A timeout leaves the client usable.** The REQ channel is re-initialized before
  `DreamTimeout` propagates, and the previous socket is closed rather than leaked (a fix over
  the reference client).
- **Observation and action keys are flat dotted names**, `<group>.<key>`, mirroring the
  embodiment spec.
